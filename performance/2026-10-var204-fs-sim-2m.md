# var204: 2M-file fs-sim tree, mongoose vs rsync (2026-10-14/15)

One NFSv3 copy, resync, and verification of the same tree, run by
mongoose and by rsync from the same client.

## Setup

- **Server:** VAST cluster var204, `main.selab-var204.selab.vastdata.com`.
  Round-robin DNS gives six VIPs, 172.200.204.1 to .6. The source export is
  `/source` and the destination export is `/dest`.
- **Client:** Ubuntu 24.04, kernel 6.12.41, 8 vCPUs (EPYC 7402P), 11 GB RAM,
  10 GbE vmxnet3 NIC.
- **Tree:** built by `fs-sim populate` from `config.yaml`. It holds 2,000,000
  regular files and 4,764 directories, 1,074,261,007,264 bytes in all, owned
  by uid/gid 1001 to 1012.
- **rsync:** version 3.2.7, run through kernel mounts with `vers=3`,
  `nconnect=8` and 1 MiB rsize/wsize. Each mount is on one VIP.
- **mongoose:** run with the default `--parallel 32`.
  - The initial copy and first cutover used a build of `1db3292`, which
    connects to one VIP.
  - The resync and second cutover used a build of `2fb8cfc` (PR #24), which
    spreads its connections over all six VIPs.

## Results

| | rsync | mongoose |
|---|---|---|
| Initial copy | 6 h 00 min 26 s (49.7 MB/s) | 17 min 35 s (1.02 GB/s), plus a 10 s scan |
| Resync after 560 changes | 21 min 15 s | 49 s |
| Verify both sides byte for byte | (not run) | about 30 min on one VIP; 28 min 39 s on six VIPs |

The resync followed `fs-sim update`, which ran for 60 s and made 560
changes:

| Change | Count |
|---|---|
| Files created | 226 |
| Files deleted | 110 |
| Files appended | 117 |
| Metadata changes | 81 |
| Files touched | 26 |

- **What the resync moved:** both tools moved 2,439,835 bytes. rsync
  transferred 450 files. mongoose copied 563 rows: the same files, plus 113
  directories whose entries changed.
- **Deletions:** neither tool propagated the deletions. rsync ran without
  `--delete`. mongoose recorded them in `classify/deleted.jsonl`, and they
  were removed from `/dest` before the cutover.

### Scan memory after walker `f6f7572` (PR #26)

The 2.4 to 2.7 GB peaks came from the embedded walker. It held every scanned
entry until the scan ended: per-shard worker batches and 256K-row row groups
are never filled by a 2M-entry tree. Walker `f6f7572` caps each worker's
pending entries and closes row groups at a shared 64 MiB byte budget.
Re-measured from `main` `55a2ed8`:

| Run | Wall | User CPU | System CPU | Peak RSS |
|---|---|---|---|---|
| mongoose no-op sync | 0:36 | 24 s | 12 s | 637 MB (was 2.30 GB) |
| mongoose cutover (six VIPs) | 28:35 | 2,764 s | 4,505 s | 860 MB (was 2.74 GB) |

The cutover passed with 0 mismatches. The sync classified all 2,004,879
entries as unchanged against a baseline the old walker wrote.

### Where mongoose's time went

**Resync (49 s):**

| Step | Time |
|---|---|
| DNS discovery of the six VIPs | 19.7 s |
| Source scan | 5 s |
| Rewrite and classify | 13.5 s |
| Copy | 7 s |

**Cutover (28 min 39 s):**

| Step | Time |
|---|---|
| Discovery | 10 s |
| Source rescan and classify | 28 s |
| Destination scan | 15 s |
| Namespace check | 12 s |
| Content read-back of 1,999,921 files | 27 min 42 s |

The read-back ran at about 646 MB/s per side, against about 620 MB/s on one
VIP.

### VIP spread (PR #24)

Copying `/source/data` (197,816 entries, 110 GB) with 32 pairs spread over all
six VIPs took 100 s at 1.10 GB/s. Each VIP carried 166 to 230 MB/s each way.
The cutover of that copy read back both sides in 168 s.

## Notes

- **rsync's cost tracks tree size.** It is a single serial stream through
  the kernel client, so its time goes to one lookup at a time on each of the
  2M files on both sides. That is why even a 2.4 MB resync took 21 minutes.
- **The client link is the ceiling.** mongoose's copy and read-back run near
  this client's 10 GbE line rate, so spreading over six VIPs gained only about
  4 to 8% here.
- **Open issues:**
  - After the scan, mongoose's own rewrite and classify state is about
    440 MB for 2M entries, and it grows with the number of entries.
  - DNS discovery takes 10 to 20 s and dominates small resyncs.
